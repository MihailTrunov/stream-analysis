# SCRUM-108 — run code-version lineage

Status: implementation design based on the approved Story and linked MVP architecture, 2026-09-30.

The existing immutable `run_snapshots` row already holds `build_id`, the resolved detection configuration, and the optional evaluation plan. CodeVersion is a one-to-one extension of that row: full Git revision when available, dirty state (`true`, `false`, or unknown), explicit capture status, and source. This is preferable to a separate CodeVersion table for the MVP because every run has exactly one capture at creation, and downstream records already refer to the run. Repeating the revision on each DetectorEvent would duplicate lineage and risk disagreement. A separate table remains possible if multiple build identities per run ever become a requirement.

The revision provider is injected at snapshot creation. The default provider first uses build-pinned environment metadata, then inspects a local Git checkout, and returns explicit `unavailable` if neither exists. The supported Compose wrapper captures Git metadata before launch because `.git` is excluded from the image. A revision with an unknown dirty flag is *not* a clean committed build. Capture is observational: malformed or missing runtime metadata becomes an unavailable state and does not alter detection or evaluation hashes, event order, or run behavior. The replay creation service passes the provider through; evaluation snapshot creation uses the same persistence entry point. Existing snapshots are migrated to explicit legacy-unavailable state rather than claiming their old free-form build ID is a Git revision.

Tests cover clean, dirty, unknown-cleanliness and unavailable capture; persisted replay/evaluation association; legacy migration; and hash independence. Event lineage traverses `DetectorEvent → PatternInstance → RunSnapshot → CodeVersion`. OutcomeObservation is not yet implemented; its future run reference must use the same traversal. Durable evaluation preflight may consume `CodeVersion.is_clean_committed` when the evaluation-job story adds the submission path. Export manifests are likewise implemented in their own later story.
