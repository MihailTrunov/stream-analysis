# Historical chart analysis 504

The installed build 2f838bd returned a POST /api/analysis 504 at 17:13:19 UTC. Nginx recorded an upstream response-header timeout while another historical chart calculation and response were running. A subsequent analysis view returned 90,622,485 bytes. API/database health remained available; this was not the calendar or provider-price request failing.

The affected persisted request used a 725-M1 source revision, two enabled 1m detectors (compression and continuation), automatic historical calculation, and a selected interval of 20:06–20:30 UTC on 6 November. Its chart view requested a 500-candle context. The source/request fixture was read from the installed database and Parquet into temporary storage; no installed runs were launched, stopped or changed by verification.

## Causes and correction

DetectorStream eagerly serialized every immutable MarketStateFrame to complete debug JSON and parsed it back for its observation list. Each candle consequently duplicated accumulated SwingPoint and SwingStructure histories. The view endpoint returned those audit histories as chart observations even though the renderer needs scalar overlay values, active-leg identifiers and per-bar marker summaries. The original fixture contained about 18 MB of repeated swing-point data and 70 MB of repeated structure data across 500 observations. Serialization also consumed CPU before the analysis POST could finish.

The web historical hook could start another POST when viewport parameters changed while a previous calculation was in flight. Those synchronous calculations contend for the same manager lock and can outlive the proxy timeout. Completed requests then retrieve large responses, adding further serialization and browser load.

RecordedFrame now retains the runtime's detached immutable frame, provides complete canonical observation mapping lazily for audit/parity consumers, and exposes a separate compact chart projection. The projection does not traverse cumulative arrays or nested structural lineage. Scalar component overlays, availability, active-leg scalar values and marker identities/times/types/labels remain available. Detector events, persisted context, formulas, configuration hashes, initialization origin and analytical calendars are unchanged. Existing contextual candle-buffer semantics remain; this change does not truncate analytical initialization or change detector results.

Historical calculation now permits one in-flight request per hook/tab, including across source/settings changes. Obsolete completions are discarded and their temporary sessions stopped; when the request completes, automatic scheduling rechecks the latest viewport. Cached coverage prevents an unnecessary follow-up. Manual live-history controls are disabled while that calculation runs. No proxy timeout was increased.

## Verification

The exact fixture was profiled in isolated SQLite/Parquet. Instrumented launch time fell from 114.31 to 61.99 seconds (profiling adds overhead); chart JSON preparation fell from 9.41 to 0.18 seconds, and the response from 90,619,126 to 2,256,684 bytes. The difference in response length versus installed logs reflects transport/run identifiers, not different price data.

The same request was then sent through a disposable production nginx/API pair using the existing images, current source mounted read-only, the copied canonical fixture and a complete temporary SQLite schema. Nginx retained its default 60-second timeout. POST /analysis returned **201 in 22.26 seconds**; its 500-candle view returned **200 in 0.615 seconds**, **2,254,591 bytes**. The installed services and data were left untouched. This verifies the reported request; calculation remains synchronous and larger workloads can still need architectural work.
