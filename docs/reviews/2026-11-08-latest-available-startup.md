# Latest-available startup history correction

The user's installed application was running build c4e65bd with a healthy database/API/workers and configured provider credentials. Read-only logs showed POST /live/prepare/US30 returning 422. A local calendar reproduction confirmed that both configured instrument profiles reject 8 November because their verified analytical coverage ends on 6 November. Retained real US30 candles already include Friday's close, but the UI waited for successful live preparation/connection before displaying them.

The correction separates price availability from live analytical availability. Startup immediately reads retained provider prices for the selected instrument where present. Freshly prepared history is also displayed before a live connection succeeds. Preparation selects the latest completed calendar candle across closed periods, rather than assuming a completed candle exists at the current clock minute. The initial target remains 1,440 completed M1 trading candles plus required initialization, reusing shared retained coverage before scheduling missing imports.

Beyond verified calendar coverage, preparation produces an explicit calendar_unverified history plan bounded to that calendar's verified interval. It does not start an unverified subscription or extend calendar definitions. The UI publishes/loads that history, identifies it as completed historical prices, and reports that current live monitoring is unavailable. The selected instrument, buffered zoom/navigation, and historical detector policies are retained. Preparation/connection failure does not erase available prices. A later live reconnect still goes through the server's unchanged account/feed/current-calendar validation.

For the reported Sunday, the latest verified completed US30 candle opens at 2026-11-06T21:59:00Z (available at 22:00 UTC); DAX opens at 20:59 UTC (available at 21:00 UTC). These are candle timestamps, distinct from a retained manifest's coverage endpoint, which may include scheduled closed intervals. The current calendar still requires the established reviewed/versioned extension procedure before live operation on later analytical dates. This fix does not relabel old data as current live data or claim new provider acceptance.

Verification: 48 existing Python live/history-range tests and 4 new calendar-boundary cases passed. The latter cover both instruments after calendar expiry, a verified closed weekend and DAX's verified Easter closure. All provider transport in regression tests was mocked and all test storage isolated. Installed diagnostics, logs and source date/count metadata were read only; installed containers and data were not changed, no credentials were displayed, and no new real provider request was made. Unrelated untracked review documents were preserved. Re-run pnpm start to rebuild the installed application with this correction.
